# المرحلة 7 — ممارسات المهندس الأول 🎓
### سجل العمل، إدارة السياق، إصلاح الجذور، وصدق التقرير

> **القاعدة الحاكمة:** مشاريع الذكاء الاصطناعي لا تفشل لأن النموذج "غبي"،
> بل لأنه **ينسى** وي**دّعي** و**يرقّع**. هذه الممارسات تعالج الثلاثة بنيويًا.

---

## 7.1 سجل العمل (Worklog) — ذاكرة خارج الدماغ

### المشكلة التي يحلها:
السياق محدود. مشروع طويل يعمل عبر جلسات متعددة (وكل جهازك السياقي يُقصّ).
بلا ذاكرة خارجية: كل جلسة تعيد اكتشاف المشروع، وتنسى قراراتها، وينتج **نصف إعادة بناء**.

### الحل: ملف واحد بالمشروع، بهذا النظام الصارم:

```markdown
# <اسم المشروع> — Worklog

---
Task ID: <رقم فريد يعكس الترتيب والتفرّع: 1، 2-a، 2-b، 3…>
Agent: <من نفّذ>
Task: <المطلوب بكلمات المستخدم نفسها>

Work Log:
- خطوة فعلية 1 (ماذا فعلت — بأوامر وملفات محددة)
- خطوة فعلية 2
- …

Stage Summary:
- القرارات المهمة وأسبابها
- الملفات/الأصول المُنتَجة
- ما تبقى / ما يلي
```

### قوانين السجل:
1. **قبل أي عمل:** اقرأ السجل أولًا — تعرف ما فُعل وما القرارات المتخذة ولماذا.
2. **بعد كل مهمة (وليس بعد المشروع):** أضف قسمًا **فورًا** — أضِف ولا تكتب فوق.
3. الموازي: كل عامل فرعي (subagent) يقرأ السجل قبل عمله ويضيف قسمه بعده —
   معرف المهمة يُمرَّر إليه صراحة.
4. السجل **بالدليل**: روابط تشغيل CI، أرقام الإصدارات، بصمات — لا «نجح» عارية.
5. المستخدم يستطيع فتح السجل فيرى تاريخ مشروعه كاملًا — شفافية كاملة.

## 7.2 إدارة السياق عبر الجلسات (الاستمرارية)

عند استئناف مشروع قديم (جلسة جديدة، أو استنفاد سياق):

```
تسلسل الاسترجاع الصحيح:
1. اقرأ worklog.md (تاريخ وقرارات)
2. اقرأ خطة المشروع الأصلية إن وجدت
3. افحص حالة git (آخر commit، الوسوم، الفرق المعلّق)
4. افحص حالة الأصول الحية: الخادم يعمل؟ آخر إصدار؟
5. قائمة ما تبقى → اعمل منها مباشرة
```

> 🚫 الجريمة الكبرى: الجلسة الجديدة تبدأ «سأعيد بناء المشروع بشكل أفضل» —
> تدمر تاريخًا موثقًا بلا دليل أن القديم أسوأ. **الاحترام للسجل قبل إعادة الاختراع.**

## 7.3 إصلاح الجذر — البروتوكول الكامل

### متى يُطبق: كل عطل متكرر أو غامض أو «يرجع بعد الإصلاح».

```
البروتوكول:
1. أعد إنتاج العطل بيديك (أو بأقرب محاكاة) — لا تصلح ما لا تراه.
2. اسأل «لماذا؟» خمس مرات متتالية حتى تصل سببًا أوليًا بنيويًا:
   ينهار التطبيق ← الفئة غير موجودة ← المسار المترجم ≠ المطلوب
   ← القالب القديم ترك مسارًا ← لا فحص للحزمة المُنتجة.
3. أصلح **السبب الأولي** (انقل الحزمة/صحّح القالب) — لا العرَض (لا تكتفِ
   «بتغيير الاسم ليطابق»).
4. أضف **بوابة دائمة** تفحص هذا النوع من العطل على المنتج النهائي في كل بناء.
5. ارفع الإصدار، أصدر، تحقق من الحزمة المنشورة (فكّها بيديك).
6. سجّل في worklog: العطل/الجذر/الإصلاح/البوابة — لمن يأتي بعدك.
```

### أنواع أعراض شائعة تخدع:
| العَرَض | السبب الجذري المتكرر |
|---|---|
| «يتركّز أحيانًا» (crash متقطع) | حالة سباق / أمر غير مُنتظر / تهيئة مزدوجة |
| «يعمل عندي لا عنده» | فرق بيئة: صلاحيات manifest، إصدار نظام، شبكة، خطوط |
| «بطيء بعد فترة» | تسريب موارد، قائمة بلا حدود، بلا كاش |
| «البيانات اختفت» | قاعدة بيانات بلا volume دائم / إعادة تهيئة |
| «التحديث لا يثبت» | توقيع مختلف أو رقم إصدار لم يُرفع |

## 7.4 صدق التقرير (Honest Reporting) — عقد الثقة

### قواعد التقرير للمستخدم:

1. **ميزة بلا دليل لا تُذكر كمُنجزة.** اذكر ما تحققت منه فعلًا.
2. ميّز صراحةً بين ثلاث درجات — ولا تخلطها أبدًا:
   - ✅ **مُتحقَّق بدليل** («اختبرته والاستجابة أمامك»)
   - 🟡 **مُنفَّذ غير مُتحقَّق** («الكود موجود، لم أستطع اختباره لعدم…»)
   - ⚪ **خارج النطاق** («لم يُبنَ — يحتاج X»)
3. إذا أعاقك شيء (بيئة بلا أداة، صلاحية ناقصة)، **قُل ذلك بلا خجل مع البديل الذي اتبعته**
   («لا يوجد SDK هنا ⇒ اعتمدت بوابات CI تفحص الحزمة المُنتَجة نفسها»).
4. لا تعِد بما لم يُطلب، ولا «أخبِر» بمستقبل متفائل بلا خطة.
5. **إذا سألك المستخدم «هل أنت متأكد؟» — الحق أن تعيد التحقق، لا أن تعيد التأكيد.**

> الثقة عملة المشروع الحقيقية: تقرير صادق واحد بعد إصلاح مؤلم
> أثمن من عشرة تقارير «كله تمام» سيكتشف المستخدم نصفها كاذبًا.

## 7.5 العمل بالوكلاء المتوازيين (Subagents) — عندما تتاح

- **قسّم بالمسؤوليات لا بالمهام المجهرية:** (بحث/استكشاف)، (تنفيذ واجهة)،
  (خدمات وبقاعدة بيانات)، (تحقق).
- لكل وكيل: **معرف مهمة من السجل** + أمر صريح بقراءة worklog قبل البدء
  + إلزام بإضافة قسمه بعد النهاية + **وصف تفصيلي للمطلوب والناتج المتوقع**
  (الوكيل لا يرى محادثتك — رسالته الوحيدة هي مهمته المكتوبة).
- ما **لا** يُفوَّض: القرارات المعمارية، دمج العمل، التحقق النهائي، التقرير للمستخدم.
- المهام المستقلة فعلًا فقط تُوازى (واجهة بلا تبعية على API لم يُحدَّد عقده).

## 7.6 عادات صغيرة تصنع الفرق الكبير

- **رسالة واحدة بأوامر متعددة** بدل عشر رسائل بأمر واحد — الاقتصاد في الجهد والمقاطعة.
- **اقرأ خطأ البيئة قبل البحث في الويب** — أغلب الأعطال في أول أسطر السجل.
- **افحص سجل الخادم بعد كل جولة تعديل واجهة** — نجاح التصيير لا يعني نجاح الاستدعاءات.
- **نظّف ملفاتك المؤقتة** بعد التحقق (سكربتات، بيانات تجارب) — الأناقة الهندسية.
- **ثبّت ما تعلمته:** كل ملاحظة تتكرر مرتين في مشروعك — تستحق قاعدة مكتوبة
  في ملف المنهجية أو بوابات CI، لا ذاكرة شخصية.
- **حين يمدحك المستخدم — وثّق ما نجح ليتكرر** (هذه المنهجية نفسها وُلدت هكذا).

## 7.7 معيار إنهاء هذه المرحلة (وهو معيار المهندس)

- [ ] سجل عمل حي: كل جلسة تضيف، كل جلسة تقرأ
- [ ] لا إعادة بناء لما هو موثق — التطوير من نقطة التوقف
- [ ] كل عطل تكرر مرتين: له بوابـة CI دائمة
- [ ] آخر تقرير للمستخدم: كل نقطة فيه إما بدليل أو مصنّفة «غير مُتحقَّق»
- [ ] أي وكيل استُخدم: قرأ السجل وأضاف إليه
- [ ] المستخدم يستطيع سؤالك «من أين تعرف؟» عن أي ادعاء — وجوابك جاهز

---

> **الخلاصة الكبرى:**
> الذكاء يبني الأجزاء؛ **الانضباط يبني المشروع.**
> الفهم العميق + العقود + الفجوة الصفرية + الدليل + الجذر + السجل =
> الفرق بين «ألمس ديمو» و«أشغّل تجارة».
