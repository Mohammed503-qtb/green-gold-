## 2.1 نموذج البيانات أولًا (Data Model First)

### لماذا أولًا؟
- كل شاشة هي في جوهرها **عرض** لبيانات، وكل زر هو **تحويل** (Transition) عليها.
- لو اكتمل النموذج، تتبعّع بقية المشروع شبه ميكانيكي.
- لو نما عشوائيًا، ستكتشف نصفه وأنت في منتصف الواجهة — أغلى لحظة للتغيير.

### قواعد بناء النموذج:

1. **احصره في ملف واحد** (schema) هو مصدر الحقيقة الأول للبنية.
2. **كل كيان من قائمة المرحلة 1 له جدول** — لا استثناءات "سأحفظه في مصفوفة JSON".
3. **المشتق لا يُخزَّن إلا بقرار واعٍ:**
   - المتاح من المخزون = الكمية − المحجوز ← يُحسب، لا يُخزَّن (منع التناقض).
   - إجمالي الطلب يُخزَّن **Snapshot** وقت الإنشاء (السعر يتغير لاحقًا والطلب لا).
4. **التاريخ جزء من النموذج، لا ميزة لاحقة:**
   - `OrderStatusHistory`: كل تحول حالة (من→إلى، الفاعل، ملاحظة، الوقت).
   - `AuditLog`: كل فعل إداري حساس.
   - بلا هذه، مستحيل حل خلاف «الطلب كان وين؟».
5. **التفاصيل المالية تُجمَّد في مكان الحدث (Snapshot):**
   - `OrderItem` ينسخ اسم المنتج والسعر والصورة وقت الطلب —
     لأن الدفعة ستنتهي والسعر سيتغير، والفاتورة لا.
6. **علاقات صريحة مع قيود** (FK) — لا حقول `id` سائبة بلا معنى مرجعي.
7. **الحقول العددية للنقود Integer** (بوحدة صغرى مثل هللة/فلس) — تجنّب فخ floating-point.
8. **لا أنواع قائمة (lists) في الحقول البدائية** — جدول مرتبط بدلها.

### اختبار اكتمال النموذج («أسئلة المحاسب»):
- «أرني كل تحركات هذه الدفعة» → `InventoryMovement` ✓
- «من غيّر حالة هذا الطلب؟» → `OrderStatusHistory` ✓
- «من قبل هذا الدفع ومتى؟» → `Payment.status/staffId/verifiedAt` ✓
- «كم طلبًا ألغى هذا الموظف هذا الشهر؟» → `AuditLog` ✓
- «أي عميل اشترى هذه الدفعة؟» → عبر `OrderItem` ✓

أي سؤال لا جواب له من النموذج = **فجوة بنيوية** أصلها الآن.

## 2.2 ملف العقود (Contracts) — قلب المنهجية

أنشئ **ملفًا واحدًا** (مثال: `contracts.ts`) يعرّف **كل ما تتفق عليه الطبقات**:

```ts
// contracts.ts — مصدر الحقيقة الواحد
export const ORDER_STATUSES = ['PENDING_PAYMENT', 'PAYMENT_SUBMITTED', 'CONFIRMED',
  'PREPARING', 'READY_FOR_DELIVERY', 'OUT_FOR_DELIVERY', 'DELIVERED',
  'CANCELLED', 'PAYMENT_REJECTED', 'REFUNDED', 'FAILED_DELIVERY'] as const;

// من يستطيع الانتقال؟ (آلة الحالة المُصرَّحة)
export const ORDER_TRANSITIONS: Record<string, { to: string; roles: Role[]; action: string }[]> = {
  PENDING_PAYMENT: [
    { to: 'PAYMENT_SUBMITTED', roles: ['CUSTOMER'], action: 'submit_payment' },
    { to: 'CANCELLED',          roles: ['OWNER', 'MANAGER', 'STAFF'], action: 'cancel' },
  ],
  PAYMENT_SUBMITTED: [
    { to: 'CONFIRMED',        roles: ['OWNER', 'MANAGER'], action: 'verify_payment' },
    { to: 'PAYMENT_REJECTED', roles: ['OWNER', 'MANAGER'], action: 'reject_payment' },
    { to: 'CANCELLED',        roles: ['OWNER', 'MANAGER'], action: 'cancel' },
  ],
  // ... كل حالة حتى DEAD-ENDS (المرفوض له مخارج: إعادة إرسال أو إلغاء)
};

// الصلاحيات: دور × فعل
export const ROLE_PERMISSIONS = {
  verifyPayment:  ['OWNER', 'MANAGER'],
  manageBatches:  ['OWNER', 'MANAGER', 'STAFF'],
  refund:         ['OWNER', 'MANAGER'],
  manageSettings: ['OWNER'],
  // ...
};

// الثوابت المشتركة
export const RESERVATION_MINUTES = 30;
export const OTP_LENGTH = 4;
```

### قواعد ملف العقود:
1. **يُعرَّف مرة واحدة** — وتُطابقه كل الطبقات:
   - الخادم يستورده حرفيًا.
   - تطبيق الموبايل له **نسخة مرآة** بنفس القيم (`constants.dart`) مع تعليق
     `// مطابق لـ contracts.ts — حدّثهما معًا`.
2. **أي إضافة حالة/صلاحية تبدأ من هنا** ثم تنتشر — العكس ممنوع.
3. **الترجمة في العميل لا في العقود**: العقود ترسل الرمز `'DELIVERED'`
   والعميل يملك قاموس العرض `{'DELIVERED': 'تم التسليم'}` — بلا نصوص عربية في قواعد البيانات.
   (الرموز ثابتة عبر كل الأنظمة؛ الترجمة محلية قابلة للتحسين بلا تعديل بيانات).
4. يُوثَّق في رأسه: *«أي تعديل هنا = تعديل مقارن في كل المرايا»*.

## 2.3 تصميم عقود الـ API

### القواعد الذهبية:

1. **تسمية متوقعة ثابتة** — REST بمعناه الصريح:
   ```
   GET  /api/catalog                 ← قائمة العرض العام
   GET  /api/batches/:id             ← تفاصيل عنصر
   GET  /api/checkout-data           ← كل ما تحتاجه شاشة الإتمام بنداء واحد
   POST /api/orders                  ← إنشاء
   GET  /api/orders/:code?phone=…    ← تتبع بملكية مُتحقَّقة
   POST /api/orders/:code/payment    ← إجراء على عنصر (sub-resource)
   POST /api/admin/orders/:id/action ← إجراء إداري
   ```

2. **غلاف استجابة موحد:**
   ```json
   // نجاح
   { "order": { ... } }              // المفتاح يسمي الكيان
   // فشل — دائمًا عربية مفهومة للمستخدم النهائي
   { "error": "المتاح من هذه الدفعة 2 حزمة فقط" }
   ```
   - رسالة الخطأ **صالحة للعرض كما هي** — لا `"MSG_402"` ولا stack trace.

3. **الخادم يعيد التجميعات الجاهزة للشاشة** (BFF mindset):
   - شاشة الإتمام تحتاج: مناطق + طرق دفع + رسوم → `GET /checkout-data` **نداء واحد**.
   - شبكة ضعيفة = نداءات أقل أهم من نداءات "أنيقة" أكاديميًا.

4. **DTO صريح لكل نقطة نهاية** — لا تسريب صفوف قاعدة البيانات خامًا:
   - الحقول الداخلية (hashedPin, internalNote) لا تظهر أبدًا في استجابة عامة.
   - DTO التتبع يعرض ما يلزم شريط التقدم فقط.

5. **الملكية تُتحقق في كل نقطة وصول:** طلب برمز `ZG-1234` + هاتف غير صاحبه = `403`
   برسالة «رقم الهاتف لا يطابق هذا الطلب». لا اعتماد على "الغريب لن يخمن الرمز".

6. **الإنشاء عبر POST يعيد الكيان كاملًا بعد الإنشاء** — العميل لا يعيد الجلب.

## 2.4 تصميم الأمان قبل الواجهة

أجوبة القبعة الحمراء تتحول إلى قرارات معمارية:

| التهديد | القرار المعماري |
|---|---|
| عميل يعدّل الأسعار في جهازه | **الخادم يعيد حساب الإجمالي من قاعدة البيانات دائمًا** — مصفوفة السلة تُرسل `batchId+qty` فقط، والسعر يُقرأ من السجل |
| سلة تحسب الخادم غير المتوقع | كل عنصر يُتحقق: موجود؟ نشط؟ متاح؟ الكمية منطقية (1..50)؟ |
| ملكية الطلب | مطابقة الهاتف في كل GET/POST يخص الطلب |
| موظف يعتدي على الصلاحيات | `requireStaff(permission)` في كل نقطة إدارية + AuditLog |
| منصات القبول/الرفض المالي | الفعل المالي يقبل OWNER/MANAGER فقط (العقود) |
| الرمز يُخمَّن | orderCode بلا تسلسل قابل للتخمين + حد معدل طلبات |
| بيانات إدارية للعامة | **فصل تام**: مسارات `/api/admin/*` عن `/api/*` + ترويسة مصادقة الموظف |

> 📌 اكتب هذه الجدول في ملف التصميم — يتحول لاحقًا إلى اختبارات المرحلة 4.

## 2.5 القرارات المعمارية الكبرى — دوّنها وبررها

لكل قرار كبير، سطران: **القرار** و**لماذا** (يقرؤهما من يأتي بعدك — ومنه أنت بعد نسيان):

```
• Prisma + SQLite: نشر بملف واحد بلا خادم قواعد — مناسب حجم المشروع وبساطة التشغيل.
• دارتًا بلا حسابات مستخدمين: الهاتف هوية، العميل يصنع نفسه عند أول طلب.
   → لماذا؟ احتكاك تسجيل أقل؛ الملكية عبر مطابقة الهاتف.
• إثبات الدفع بصورة مرفوعة + تحقق يدوي إداري → لا بوابة دفع (لا حساب تاجر بعد).
• تطبيق أصلي Flutter لأن الجمهور موبايل 100% وكاميرا مطلوبة لإثبات الدفع.
```
