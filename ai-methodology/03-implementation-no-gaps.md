# المرحلة 3 — التنفيذ بلا فجوات 🔨
### قواعد صارمة تحوّل التصميم إلى نظام كامل يعمل من طرف إلى طرف

> **القاعدة الحاكمة (الفجوة الصفرية):** أي تدفق يبدأ يجب أن ينتهي بنتيجة مرئية.
> أي حالة في آلة الحالة يجب أن تكون قابلة للوصول **ومن** كل شاشة يخرج مخرج واضح.

---

## 3.1 ابنِ عموديًا لا أفقيًا (Vertical Slices)

**النمط الفاشل:** كل الواجهات أولًا، ثم «نربطها بالخادم لاحقًا».
هذا "لاحقًا" هو مقبرة المشاريع — تكتشف وقت الربط أن التصميم لا يتطابق.

**النمط الصحيح — تدفق واحد كامل من طرف إلى طرف:**

```
شاشة ← زر ← API ← تحقق ← قاعدة بيانات ← أثر جانبي (سجل/إشعار) ← استجابة ← عرض النتيجة
```

نفّذ رحلة المستخدم **الأهم** كاملة أولًا (مثال تجاري: تصفّح ← سلة ← طلب ← دفع ← تتبع).
ثم الرحلة الثانية (الإدارة: تحقق ← تجهيز ← توصيل ← تسليم بـ OTP).
كل رحلة تُنجز **كاملة** قبل التالية — النتيجة: في أي لحظة، ما يعمل يعمل فعليًا.

---

## 3.2 قواعد الشاشات (لا طرق مسدّدة)

كل شاشة في التطبيق تُجيب عن ثلاثة — وإلا فهي ناقصة:

1. **كيف يدخل المستخدم البيانات؟** — حقل، اختيار، رفع…
2. **كيف يتقدم؟** — زر «متابعة/تأكيد/إرسال» **ظاهر دائمًا** وقابل للنقر عند صحة المدخلات.
   > 🚫 أخطر عطل تجربة: شاشة تفاصيل بلا زر متابعة — المستخدم محبوس.
   > القاعدة: أزرار التنقل في شريط سفلي **ثابت** (`bottomNavigationBar`) لا يختفي
   > مع لوحة المفاتيح ولا التمرير — ويعطَّل بصريًا فقط عند نقص المدخلات، مع إظهار
   > للمستخدم **ماذا ينقص** عند محاولة التقدم.
3. **كيف يخرق/يتراجع؟** — رجوع، إلغاء، «سأتسوق لاحقًا».

### حالات كل شاشة (٤ حالات إلزامية):
| الحالة | شكلها |
|---|---|
| **تحميل** | هيكل (Skeleton) — لا دوّار أبدي |
| **فارغة** | رسالة + زر فعل («السلة فارغة — تصفح الدفعات») |
| **خطأ** | رسالة عربية من الخادم + زر «أعد المحاولة» |
| **نجاح** | البيانات + الأزرار |

> صوت المترجم الفاسد: «الحالات الفارغة والخطأ نضيفها بعد الربط» — كذبة؛
> الربط لا يجيء إلا والفجوات ازدادت. ابنِ الأربع حالات من أول نسخة.

## 3.3 قواعد الخادم (الأمان سلوك لا ميزة)

1. **الأسعار من الخادم فقط:**
   ```ts
   // الطلب الوارد
   { items: [{ batchId, qty }] }   // لا سعر مُرسَل من العميل إطلاقًا
   // الخادم
   const batch = await tx.productBatch.findUnique(...);
   lines.push({ unitPrice: batch.price, ... });  // السعر من قاعدة البيانات
   ```
   والواجهة تعرض سعرًا **توقّعيًا** بوسم «تقديري» إن أمكن — الحقيقة النهائية عند الخادم.

2. **كل تحويل حالة يمر بآلة العقود** — لا `update({status: 'X'})` مباشرة:
   ```ts
   const allowed = ORDER_TRANSITIONS[order.status].find(t => t.action === action);
   if (!allowed) throw new ApiError('لا يمكن هذا الانتقال في الحالة الحالية', 409);
   if (!allowed.roles.includes(currentRole)) throw new ApiError('لا تملك صلاحية هذا الإجراء', 403);
   ```
   مع كل انتقال: سجل تاريخ + إشعار + **الأثر الجانبي** (تحرير/خصم مخزون، توليد OTP…).

3. **العمليات المالية والمخزنية داخل معاملة واحدة (Transaction):**
   إنشاء الطلب = تحقق توفر + حجز + سجلات + إشعار **ككتلة تُنجز أو تفشل كلها**.
   > لا تنسَ **تحرير الحجوزات المنتهية** قبل التحقق من التوفر (وظيفة دورية/قبل كل طلب).

4. **رسائل الخطأ عربية مفهومة + كود حالة صحيح:**
   - `400` مدخلات، `401` جلسة، `403` ملكية/صلاحية، `404` غير موجود، `409` تعارض حالة، `500` الخادم.
   - الرسالة تشرح **ماذا يفعل المستخدم**: «الدفعة نفدت أثناء إتمام طلبك — تصفح دفعات أخرى».

5. **كل فعل إداري حساس = سطر تدقيق:**
   `logAudit(staff, 'REFUND', orderId, note)` — بلا استثناء ولا "سأضيفها لاحقًا".

6. **كلمات السر/PIN لا تُخزَّن ولا تُعاد:** تُقارن في الخادم، ولا تظهر في أي استجابة/سجل.

## 3.4 قواعد العميل (تطبيق الموبايل/الويب)

1. **مرآة العقود:** كل حالة/تسمية/لون في `constants.dart` مطابق لملف العقود — بنفس التعليق المرجعي.
2. **أخطاء الشبكة لها كيان:**
   - مهلة قصيرة (connect 8s / receive 20s) — الشبكة الضعيفة تُفشل سريعًا وتعرض البديل.
   - استجابة `error` من الخادم تُعرض كما هي (فهي عربية أصلًا).
   - انقطاع: «تعذر الاتصال — يعرض ما حُفظ» لا جمود صامت.
3. **الأدوار على الشاشة:** زر لا يظهر لمن لا يملك صلاحية فعله (من العقود) —
   الإخفاء تجربة، **والتحقق في الخادم هو الأمان**. كلاهما مطلوب.
4. **الأرقام والعملة والتواريخ بأداة تنسيق واحدة** في كل التطبيق — لا `toString()` بدائي.
5. **إعادة المحاولة صناعة العميل:** الرفع الفاشل لإثبات الدفع يعرض «أعد المحاولة»
   بنفس البيانات المحفوظة محليًا — لا يعيد المستخدم ملء كل شيء.
6. **الهوية من أول استخدام بلا احتكاك:** أدخل هاتفك عند أول طلب، ودعه يتذكّره.

## 3.5 التدفق الكامل — قائمة تحقق لكل رحلة مستخدم

لكل رحلة في الخطة (كرّر هذه القائمة):

```
□ شاشة البداية: ٤ حالات (تحميل/فارغ/خطأ/نجاح)
□ أول تفاعل → استجابة الخادم → عرض النتيجة
□ نجاح → ينتقل للخطوة التالية (زر ظاهر)
□ فشل → رسالة + إعادة محاولة بلا فقد بيانات
□ انقطاع شاملة → البيانات المحلية تبقى + مزامنة عند العودة
□ النهاية السعيدة → نقطة نهاية واضحة (شاشة نجاح + رقم مرجعي + زر متابعة)
□ النهاية التعيسة → (رفض/إلغاء/فشل) → ماذا يرى المستخدم وماذا يفعل بعدها؟
□ الأثر الخلفي → سجلات + إشعارات + مخزون حسب قواعد العمل
```

> تتبّع الرحلة بإصبعك على الشاشة فعلًا: **اذهب خطوة خطوة ولا تفتح شاشة جديدة
> قبل أن تعرف أين زر خروجك منها.** الطريق المسدود الواحد يهدم ثقة المستخدم بالكل.

## 3.6 البيانات الأولية (Seed) — جزء من المنتج لا من الاختبار

بذرة واقعية تغطي **كل** الحالات التي ستعرضها الواجهات:
- كيانات كاملة بأسماء وصور وأسعار منطقية للسوق المستهدف.
- دفعات بمخزون **متفاوت**: نفد، منخفض، وفير — لتختبر كل شارات الحالة.
- طلبات عينية في كل حالة من آلة الحالة — لتختبر كل ألوان الشارات وقوائم التتبع.
- حسابات أدوار كاملة (مالك/موظف/سائق) بـ PIN.
- إعدادات جاهزة (اسم المتجر، تواصل).

> الفائدة: كل شاشة ترى بيانات من أول تشغيل = تكتشف الفجوات البصرية والمنطقية فورًا.

- [ ] كل رحلة في قائمة 3.5 مكتملة الأعمدة (شاشة→API→قاعدة→أثر→عرض)
- [ ] كل شاشة بحالاتها الأربع + زر تقدم ظاهر + مخرج واضح
- [ ] لا تحويل حالة خارج آلة العقود، ولا سعر من العميل، ولا فعل إداري بلا تدقيق
- [ ] رسائل الخطأ كلها عربية قابلة للعرض كما هي
- [ ] البذرة تغطي كل الحالات والأدوار
- [ ] (بيئة ضعيفة) كاش القراءة + فشل سريع + عرض المحفوظ
